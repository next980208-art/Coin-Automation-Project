## 5분 발표 대본

안녕하세요. 저는 Binance USDT-M 선물 데이터를 수집하고 PyFlink로 머신러닝용 피처를 만드는
자동매매 데이터 파이프라인을 구축하고 있습니다.

전체 흐름은 과거 데이터의 경우 `Binance REST API → Airflow → PyFlink → Parquet`이고,
실시간 경로는 `WebSocket → Kafka → PyFlink`입니다. 이번 과제는 별도 예제 프로젝트를 만들지
않고 이 파이프라인에 직접 적용했습니다.

먼저 4차시 Airflow 자동화입니다. 기존에는 Python 명령에 종목과 날짜를 직접 넣어야 했지만,
현재 DAG는 `symbol`, `start_date`, `end_date`, `timeframe`, `chunk_days`를 실행 입력값으로
받습니다. 따라서 종목이나 날짜를 바꿀 때 DAG 코드를 수정할 필요가 없습니다.

[Trigger DAG 입력 화면을 보여줍니다.]

실제 Airflow 브라우저 화면에서 종목을 `SOL/USDT`, 기간을 2026-08-28부터 29일까지,
청크 크기를 1일로 입력했습니다. 아래 Generated Configuration JSON은 Airflow가 이 값을
`dag_run.conf`로 전달한다는 뜻입니다. Run ID는
`assignment4_solusdt_20260828_20260829`로 지정했습니다.

[성공 그래프를 보여줍니다.]

실행 결과 네 태스크가 모두 성공했습니다. 첫 태스크는 입력값과 범위를 결정하고, 두 번째는
Binance 데이터를 수집해 PyFlink로 가공하고 Parquet에 저장합니다. 세 번째와 네 번째는
피처 데이터와 선물 컨텍스트 데이터의 행 수, 중복, 시간 공백, 필수값 결측을 검증합니다.

결과는 OHLCV 피처 1,440행과 mark price·funding rate·open interest 컨텍스트 1,440행입니다.
timestamp 중복과 1분 공백, 필수값 결측은 모두 0건이고 두 품질 검사가 `healthy=true`였습니다.
Airflow 상세 화면에는 상태 `success`, 수동 실행, 실행 설정 JSON, 실제 실행 시간 27초가
남아 있습니다.

실행 초기에 SequentialExecutor를 먼저 실행 중이던 일일 수집 태스크가 점유해 SOL 실행이
대기했습니다. 일일 DAG를 잠시 일시정지하고 스케줄러를 재시작해 실행기를 복구했습니다.
DAG 코드는 수정하지 않았으며 대기 중이던 작업은 이후 순서대로 정상 처리됐습니다.

다음은 5차시 부하·장애·복구 실험입니다. 외부 Binance에 부하를 보내면 안 되기 때문에 저장해
둔 실제 BTCUSDT 이벤트를 로컬 Kafka에 재생했습니다. 정상 실행은 1,000건이고 부하 실행은
고유 10,000건에 중복 500건을 더한 10,500건입니다. Consumer가 중복 500건을 감지해 제거했고
PyFlink가 최종 고유 10,000행을 Parquet에 저장했습니다.

장애 실험에서는 필수 `close` 필드를 제거했습니다. 전처리 작업은 잘못된 입력을 조용히
저장하지 않고 종료 코드 1로 실패했습니다. 이후 정상 1,000건을 다시 실행해 1,000행을
복구했고 중복과 필수값 결측이 모두 0건임을 확인했습니다.

대용량 원본 Parquet와 API key는 GitHub에 올리지 않았습니다. 대신 DAG 코드, 실제 Airflow
화면, 작은 검증 JSON, 실행 로그, 결과 수치를 제출했습니다. Spark 대신 Flink를 쓴 이유는
이 프로젝트가 배치 피처와 향후 실시간 피처를 같은 처리 엔진으로 연결하도록 설계됐기
때문입니다. 감사합니다.

## 1분 요약 대본

Airflow DAG가 종목과 날짜를 입력값으로 받도록 만들어 코드 수정 없이 `SOL/USDT` 하루를
실제 실행했습니다. Airflow UI에서 생성된 JSON과 Run ID를 확인했고 네 태스크가 모두
성공했습니다. PyFlink가 OHLCV 피처와 선물 컨텍스트를 각각 1,440행 저장했으며 중복, 1분
공백, 필수값 결측은 모두 0건이었습니다.

5차시에서는 저장된 실제 이벤트를 로컬 Kafka에 재생해 정상 1,000건과 부하 10,000건을
비교했습니다. 중복 500건을 제거했고, 필수 필드 누락 장애를 안전하게 실패시킨 뒤 정상
1,000행으로 복구했습니다. 외부 서비스에는 부하를 보내지 않았고 대용량 원본과 비밀키도
제출에서 제외했습니다.

## 예상 질문

### Airflow가 데이터를 직접 가공합니까?

아닙니다. Airflow는 입력값, 실행 순서, 상태를 관리하는 오케스트레이터입니다. 실제 피처
계산은 PyFlink가 수행합니다.

### 왜 과거 배치에 Kafka를 사용하지 않습니까?

날짜 범위가 정해진 REST 데이터는 파일로 받아 PyFlink에 전달하는 편이 단순합니다. Kafka는
계속 들어오는 실시간 이벤트를 버퍼링하고 재생할 때 사용합니다.

### 왜 Spark 대신 Flink를 사용했습니까?

현재 프로젝트는 과거 배치와 향후 실시간 스트리밍에서 같은 피처 정의를 사용하려 합니다.
Flink는 두 경로를 모두 지원해 프로젝트 표준 처리 엔진으로 선택했습니다.

### 10,000건을 Binance에서 새로 받았습니까?

아닙니다. 외부 서비스에 부하를 주지 않도록 저장해 둔 실제 이벤트를 로컬에서 반복 확장해
Kafka에 재생했습니다. 가격 패턴은 원본이고 테스트용 event ID와 timestamp만 고유하게
만들었습니다.

### 현재 실거래가 가능합니까?

아직 아닙니다. 현재 범위는 데이터 수집, 피처 가공, 저장, 품질 검증, 장애 복구입니다.
실거래 주문 API는 장기 백테스트와 페이퍼 트레이딩 기준을 통과하기 전까지 연결하지 않습니다.
