## 발표 대본

안녕하세요. 제가 진행 중인 프로젝트는 Binance USDT-M 선물 데이터를 모아서 머신러닝에
사용할 피처 데이터로 만드는 작업입니다.

과거 데이터는 Binance REST API에서 받고, Airflow가 실행 순서를 관리합니다. 실제 데이터
가공은 PyFlink가 하고 결과는 Parquet으로 저장합니다. 실시간 데이터는 나중에 WebSocket,
Kafka, Flink 순서로 처리할 계획입니다.

먼저 4주차 과제입니다.

기존에는 종목과 날짜를 명령어에 직접 넣어 실행했습니다. 이 방식은 다른 종목을 받을 때마다
코드를 고쳐야 해서, Airflow 실행 화면에서 `symbol`, 시작일, 종료일, 봉 간격과 청크 크기를
입력하도록 바꿨습니다.

[Airflow 입력 화면을 보여줍니다.]

이번에는 `SOL/USDT`와 2026년 8월 28일 하루를 입력했습니다. Trigger를 누르면 화면의 값이
JSON으로 DAG에 전달됩니다. DAG 파일은 수정하지 않았습니다.

[네 태스크가 성공한 화면을 보여줍니다.]

실행 순서는 날짜 범위 결정, 데이터 수집과 PyFlink 가공, 피처 검사, 선물 컨텍스트 검사입니다.
네 작업이 모두 성공했고 피처 데이터와 선물 컨텍스트가 각각 1,440행 저장됐습니다. 중복,
1분 간격 공백과 필수값 누락은 모두 0건이었습니다.

처음에는 기존 일일 작업이 Airflow 실행기를 사용 중이라 새 작업이 대기했습니다. 일일 DAG를
잠시 멈추고 스케줄러를 다시 시작한 뒤 정상 실행됐습니다. 입력값이나 DAG 코드가 잘못된
문제는 아니었습니다.

다음은 5주차 과제입니다.

외부 거래소에 많은 요청을 보내지 않기 위해 이미 저장한 실제 BTCUSDT 1분봉을 로컬 Kafka에
재생했습니다. 평소 입력은 1,000건, 부하 입력은 고유 데이터 10,000건으로 잡았습니다.
중복 처리도 확인하려고 부하 입력에는 같은 event ID 500건을 추가했습니다.

[Flink 정상 1,000건 화면을 보여줍니다.]

정상 실행은 1,000건을 받아 1,000행을 저장했고 전체 시간은 11.141초였습니다.

[Flink 부하 10,000건 화면을 보여줍니다.]

부하 실행은 Kafka에 총 10,500건을 보냈습니다. Consumer가 중복 500건을 제거해 Flink에는
고유한 10,000건이 전달됐고 Parquet도 10,000행이 저장됐습니다. 전체 시간은 12.875초였습니다.

장애 실험에서는 필수 필드인 `close`를 한 건에서 제거했습니다. 입력 검사가 이 파일을
정상 데이터로 저장하지 않고 종료 코드 1로 멈췄습니다. 그다음 정상 입력 1,000건으로 다시
실행해 별도의 복구 결과를 만들었습니다.

[Flink 복구 1,000건 화면을 보여줍니다.]

복구 Job도 `FINISHED`였고 저장된 1,000행에서 중복과 필수값 누락은 0건이었습니다.

정리하면 4주차에는 종목과 날짜를 바꿔 다시 실행할 수 있는 Airflow DAG를 확인했고,
5주차에는 데이터 양 증가, 중복 입력, 잘못된 입력과 재실행 복구를 확인했습니다. 대용량
원본과 비밀키는 GitHub에서 제외하고 코드, 작은 결과 JSON, 로그와 실제 화면만 제출했습니다.

## 짧게 설명할 때

Airflow 화면에서 종목과 날짜를 입력해 SOLUSDT 하루 데이터를 수집하고 PyFlink로 가공했습니다.
두 결과가 각각 1,440행 저장됐고 품질 검사도 통과했습니다. 이어서 저장된 BTCUSDT 데이터를
로컬 Kafka에 재생해 1,000건과 10,000건을 비교했습니다. 중복 500건은 제거됐고 필수 필드
누락은 실패 처리한 뒤 정상 1,000건으로 다시 복구했습니다.

## 질문을 받았을 때

### Airflow가 직접 데이터를 가공하나요?

아닙니다. Airflow는 어떤 작업을 어떤 순서로 실행할지 관리합니다. 피처 계산은 PyFlink가
합니다.

### 과거 데이터 수집에도 Kafka가 꼭 필요한가요?

날짜 범위가 정해진 과거 데이터는 파일로 받아 바로 처리하는 편이 단순합니다. Kafka는
실시간으로 계속 들어오는 데이터를 잠시 보관하고 다시 처리할 때 더 필요합니다. 이번 5주차
과제에서는 저장한 이벤트를 재생하면서 부하와 중복을 확인하기 위해 Kafka를 사용했습니다.

### 왜 Spark가 아니라 Flink인가요?

이 프로젝트에서 이미 PyFlink로 배치 가공을 만들었고, 이후 실시간 가공에도 Flink를 사용할
계획이라 같은 도구를 사용했습니다.

### 10,000건을 거래소에서 다시 받았나요?

아닙니다. 외부 서버에 부하를 주지 않도록 저장한 실제 데이터의 가격 흐름을 사용하고,
timestamp와 event ID를 겹치지 않게 만들어 로컬 Kafka에서만 재생했습니다.

### 지금 실거래도 하나요?

아직 데이터 수집, 가공, 저장과 검증 단계입니다. 이 과제에는 주문 API나 실제 거래 기능이
포함되지 않습니다.
